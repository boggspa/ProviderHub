# Provider Hub Preview

**Version 0.5.6 (build 50).** Licensed Apache-2.0 — see [LICENSE](LICENSE),
with attributions in [NOTICE](NOTICE).

A native macOS menu bar app that connects Claude Desktop and the Codex coding workspace to eleven model API connections: Mistral, Kimi Code, MiMo Token Plan, Ollama, DeepSeek, Cerebras, Muse, Grok, Qwen Token Plan, OpenRouter, and the Gemini API. Claude uses the local Messages endpoint. Codex uses Responses: Grok, Ollama, and OpenRouter retain native Responses transports, while the other eight use the local Messages bridge and their provider adapters.

Provider Hub Preview retains the Preview label while additional provider accounts and desktop integration paths complete live qualification. An earlier Mistral Bridge 0.2 prototype is maintained separately and is not distributed from this repository. The two never share state: they have separate bundle IDs, settings directories, Keychain namespaces, gateway ports, and Claude profile IDs, so installing or building the preview cannot disturb the prototype.

**Start using the preview**

1. Move **Provider Hub Preview.app** to Applications and open it. It requires an Apple Silicon Mac and macOS 14 or newer. The shareable bundle includes Python 3.13.13; no separate Python installation is needed. A lightweight source build can use Python 3.11 or newer, including a runtime installed with Vibe.
2. Select a provider in **Providers**. Mistral can use the API key configured in Vibe. **Save key** stores an API key in the preview's macOS Keychain namespace and immediately fetches that provider's models. Ollama connects to the existing local daemon. MiMo's account region selects its official Token Plan endpoint.
3. Catalogues refresh in the background when the app opens. **Refresh all** and the provider card's **Refresh catalogue** remain available for retrying. Refreshes fetch metadata without generating a chat completion. Each provider reports its own errors; an unrelated provider's failed refresh does not discard other catalogues. Kimi, MiMo, and Qwen Token Plan use documented catalogues because an account-scoped list endpoint has not been established.
4. **Models** shows independent curated catalogues: Codex / ChatGPT on the left, Claude Desktop on the right. A client selector provides a full-width view and is used automatically in smaller windows. Search a catalogue, add or remove models, and expand a row for its controls. Claude rows expose the family, family default, inference test, and compaction threshold. Codex rows show subagent priority and automatic compaction at 85% of the effective input window; starting-model and default-subagent controls follow the list. Context limits remain metadata-driven and unknown limits stay unknown.
5. Existing catalogues are preserved. Legacy Claude mappings and Codex’s all-compatible selection are displayed without changing settings; the first catalogue edit materializes that selection. Legacy Claude thresholds survive migration, using the lowest explicit threshold when multiple slots share one route. The original slot mappings remain saved.
6. **Config** uses the same client arrangement for desktop preferences, launch/show, and restore actions. The shared gateway auto-stop setting sits above both panes. Claude features, Auto mode, Claude Code catalogue support, and Ultracode workflows live on the right; Codex account, appearance, file-editing, and goal-budget options live on the left. **Save changes** saves all pending preferences and explains when a desktop session must close first. Provider connections and the Activity view keep their existing roles. The old Devin Agents page is removed from primary navigation; its provider connection and backend remain available.
7. Launch the desired desktop app from **Config**. Finish current Claude work and quit Claude before switching profiles. For Codex / ChatGPT, Provider Hub first validates the selected catalogue in a disposable Codex home without submitting a model turn, prepares the gateway, and asks before restarting an already-running desktop app. The restart interrupts active desktop work, so finish that work before approving. Provider Hub switches only the owned model settings and opens the installed app.
8. Quitting a launched desktop app restores that harness's prior selection. The shared gateway stays available while either owned harness remains open and normally stops after both have closed. The menu bar app remains available.
9. While one desktop harness is live, you can still change the *other* harness's model selection (e.g., edit the Codex catalogue while Claude is running). Save writes the change without stopping the gateway; launching the second app briefly restarts the gateway so both share the new snapshot, and the running app reconnects automatically. Changing shared provider settings (keys, regions, port, branding) while either app is live still requires quitting both desktop apps first.

Build from the repository root with `bash Source/build.sh` to create `Provider Hub Preview.app` beside the checkout. `Source/build.sh` is the source of truth for both the version and the build stamp; no number is restated here, because it goes stale between releases. Building from source applies an ad-hoc development signature, which is enough to run locally; distribution builds are signed with an Apple Developer ID and notarized on the maintainer's machine, and those credentials are never committed. See [`CONTRIBUTING.md`](CONTRIBUTING.md) for setup and tests, and [`SECURITY.md`](SECURITY.md) for the signing and threat model. A shorter end-user guide is in `QUICK-START.md`.

For Mistral, Kimi, MiMo, DeepSeek, Cerebras, Muse, Qwen Token Plan and Gemini, Codex still sends `/v1/responses` to Provider Hub. The hub translates that request into its existing local `/v1/messages` contract, which then uses the same provider-specific transport already used by Claude. The local hop authenticates to the loopback gateway, consumes one place in the existing eight-request provider concurrency limit, and records the provider request once rather than double-counting the outer Responses request.

The **Vibe saved API key** option resolves the credentials configured for Vibe and uses Mistral's standard API. **Ollama memory residency**

Ollama holds a model in memory for five minutes after the turn that loaded it, and re-arms that lease at the end of every turn. Inside a conversation that is what you want: a steer, a queued message or an immediate follow-up finds the weights already loaded. Once the conversation is finished it is the opposite — an abandoned 30B model keeps its memory for five more minutes, and a session that moves between local models leaves each one resident behind it until the daemon restarts. `keep_alive` is the daemon's own control for this, but it is a native-API field, and both endpoints the hub talks to are compatibility layers: a `/v1/messages` request carrying `keep_alive: "90s"` still leaves the runner at the daemon default. The hub therefore sets the lease itself. Once a turn's upstream connection is closed — after the client has its answer, on the Messages and Responses paths alike — it asks `/api/ps` which models the daemon is holding, and when the turn's model is one of them it posts a prompt-free `/api/generate` carrying the lease. That re-arms the runner's expiry in a few milliseconds without generating a token. Eviction stays the daemon's job, so the shorter lease outlives a hub that is quit or crashes between turns. A model the daemon is not holding is never posted to, because the same call against a cold model is a preload: cloud-tagged routes, already-evicted runners and turns that never reached the weights all stop at the `/api/ps` answer, and no model other than the one the turn used is touched.

The lease is 90 seconds by default and belongs to the connection: **Providers → Ollama → Unload a finished model after** sets it, and `providers.ollama.idle_unload_seconds` in `settings.json` is that same value. The pane offers a ladder of presets and keeps any other value the file already holds rather than rewriting it. `0` unloads the model as soon as its turn ends, `-1` is Ollama's own never-expire for a machine that would rather hold weights than reload them, and the ceiling is 86400 (a day). It applies to the models the hub itself ran rather than to the daemon as a whole, and it never downloads, deletes, or restarts anything.

**Qwen, OpenRouter and Gemini**

Qwen Token Plan uses its dedicated Singapore subscription endpoint and `QWEN_TOKEN_PLAN_API_KEY`. It does not fall back to Coding Plan or PAYG. Five Qwen model limits come from TaskWraith/Pi’s matching Token Plan catalogue, with provenance recorded; newer models with unreported limits remain unknown. Qwen 3.8 exposes its actual Low/Medium/Extra High controls.

OpenRouter uses `OPENROUTER_API_KEY`. Its curated shortlist comes from TaskWraith’s Pi definitions; availability, context limits and effort levels refresh from OpenRouter. Different context limits become separate choices. The adapter sends the original model ID and restricts the permitted hosts to the selected context and requested controls. The source shortlist is not treated as proof that an old preview/free route still exists.

The curated OpenRouter roster follows the live model list rather than pinning it: when OpenRouter withdraws a model, discovery removes the choice and says so instead of leaving a dead route selectable. An OpenRouter `stealth/` preview belongs to an anonymous upstream, so there is no brand to borrow and it wears the namespace's own gold accent. `PROVIDER-ADDITIONS.md` records the withdrawn Union Alpha preview that established that treatment.

Gemini uses `GEMINI_API_KEY` from Google AI Studio, independently of CLI/OAuth and Google app subscriptions. Google’s exact input and output limits remain separate. Tool and text thought signatures are preserved through authenticated replay blocks, and Codex carries those blocks in encrypted history. Replies are currently buffered until generation finishes so final-chunk signatures are retained; the gateway sends keepalives while waiting. `PROVIDER-ADDITIONS.md` contains the contract, provenance, tests and current qualification boundaries.

**Connect Muse with a Meta Model API key**

1. Select **Muse** in Providers and use **Account setup** to open Meta's Model API console if you need a key.
2. Paste the Model API key into the secure field and choose **Save key**. The app stores it under `MODEL_API_KEY` in its own macOS Keychain namespace and fetches the account's model list automatically.
3. Choose the returned Muse model in a Claude slot or on the Codex page, then launch that desktop harness. Muse supplies model responses while the desktop client owns the tool loop; this connection does not start a Muse Code agent.

The native Messages endpoint is `https://api.meta.ai/v1/messages`; discovery uses `https://api.meta.ai/v1/models`. Both use the selected Model API credential. The environment option reads `MODEL_API_KEY`. It does not read `META_API_KEY` or copy the Muse CLI's login/credentials.

Usage follows Meta Model API billing, including any applicable preview allowance. This is distinct from the automatically connected Muse Code subscription credential, which Meta scopes to Muse Code. Do not infer the billing product from a key's shape. See the [Meta Model API cookbook](https://github.com/meta-models/meta-model-cookbook) and `NATIVE-AGENTS.md`.

Only account-listed IDs are advertised. For the exact `muse-spark-1.3` ID, Meta's cookbook reports a 1,048,576-token context and 131,072-token maximum output; more specific account metadata takes precedence when returned. Other IDs retain their own metadata and are not silently treated as aliases of Spark 1.3.

Claude's Effort control maps to Meta's current first-party Spark 1.3 ranks: Minimal, Low, Medium, High, Extra-high (`xhigh`), and Max. Ultra uses the highest advertised Meta rank (`max` on Standard-tier Spark 1.3). Reasoning cannot be disabled on Spark. A live `/v1/models` `effort_modes` list still wins when present; Contributor-tier or other narrower lists are not given Standard-tier `max`. The Codex/ChatGPT effort slider and advanced Effort menu publish those advertised ranks as `supported_reasoning_levels`. Muse Fast is not advertised. Meta's cookbook still describes `xhigh` as equal to `high` and omits `max`; Hub follows the current [reasoning](https://dev.meta.ai/docs/reasoning.md) page plus live list fields instead.

**Connect Grok with an xAI API key**

1. Select **Grok** in Providers, open **Account setup**, and use an xAI API key.
2. Save the key in the secure field. It uses the app's own `XAI_API_KEY` Keychain entry; Environment mode reads `XAI_API_KEY` from the launch environment.
3. Choose an account-listed Grok model in the Claude mappings or on the Codex page, then launch that harness. Both routes use pay-as-you-go API billing and do not import Grok Build login credentials.

Claude uses `https://api.x.ai/v1/chat/completions`; Codex uses xAI's native `https://api.x.ai/v1/responses`. xAI has deprecated its Anthropic endpoint. Discovery uses the account's language-model list to define membership and adds exact context metadata from the same account's general model list. Only the exact `grok-4.6` ID receives the documented 500,000-token fallback; unknown limits remain unknown. Catalogue presence does not prove inference access.

Claude's Effort control maps to documented Grok levels: Minimal → Low; Max/Ultra → XHigh on Grok 4.6, or High on Grok 4.5. Reasoning cannot be disabled on those models. Unknown models need advertised effort metadata before non-default effort is accepted. The Codex catalogue exposes only the known Grok effort levels and explicitly labels its Fast tier as **xAI Priority**. Priority processing carries premium token pricing. Activity metadata records the actual `service_tier` when the provider returns it; requesting Priority does not guarantee that xAI served the request at that tier. No xAI key was configured for the 0.4.0 cycle, so Grok remains protocol-verified rather than live-qualified against a provider account.

Sources: [Grok 4.6](https://docs.x.ai/developers/grok-4-6), [reasoning controls](https://docs.x.ai/developers/model-capabilities/text/reasoning), [Priority processing](https://docs.x.ai/developers/advanced-api-usage/priority-processing), [model discovery](https://docs.x.ai/developers/rest-api-reference/inference/models).

Every other Codex catalogue row likewise publishes only that model's documented effort ranks. Fast appears only when the model has a same-model Fast control. ChatGPT's Power slider is not overridden with extra model rows; after a custom model is selected, the effort slider and advanced Effort menu use those ranks, and Fast maps to the advertised service tier.

**Codex / ChatGPT Desktop**

Provider Hub exposes `/v1/responses` for every configured provider connection. Grok, Ollama and OpenRouter remain native: the hub relays their streaming and non-streaming Responses, function-call history and outputs, opaque provider reasoning items, terminal usage, provider errors, and cancellation. Mistral, Kimi, MiMo, DeepSeek, Cerebras, Muse, Qwen Token Plan and Gemini use the authenticated local Messages bridge described above, which converts JSON and streaming function calls, usage, errors, and cancellation back to Responses semantics. `client_metadata` is consumed as local client context and is never forwarded to a provider.

The route accepts function tools and Codex function namespaces. Namespaces are flattened into provider-safe function names and restored on returned calls so dispatch remains reversible across turns. Of the hosted tools only `web_search` is honoured: the generated profile turns it on when any catalogue route can serve it (Codex CLI routes, where OpenAI runs the search under the ChatGPT plan; Claude and Grok CLI routes, where Anthropic or xAI runs it under the CLI's own sign-in; and OpenRouter models with native search), and the gateway drops it for routes that cannot. The dedicated free-form `apply_patch` catalogue field is unset by default, so the installed Codex engine edits through its shell/function tooling and shows no close-out diff card for hub turns. The Codex tab's **Offer apply_patch to catalogue models** switch advertises it for every catalogue route; Provider Hub then projects Codex's free-form tool as a JSON `apply_patch(patch)` function for the provider and converts the calls back, which restores the diff card, per-file rows, Undo and Review. See `CLOSEOUT_CARDS.md`.

Ollama, OpenRouter and all eight translated connections are stateless in this integration: Codex must send full history with `store:false`, and Provider Hub rejects `previous_response_id`. Thinking-capable Ollama models publish their think ranks on the Codex/ChatGPT effort slider; Fast/service-tier controls are still not invented. Grok also defaults to `store:false`; when a client explicitly requests `store:true`, a later `previous_response_id` is accepted only for an ID previously returned under the same model, account, and credential scope. The local `response-ownership.json` holds at most 10,000 ID/scope records and no prompts or response content. Native xAI is the only route that supports response-ID continuation.

When a Messages provider returns opaque thinking needed on the next tool turn, the bridge places that provider reasoning in an authenticated encrypted Fernet envelope inside the Responses history. `cryptography` 50.0.0 uses the separate persistent local `responses-encryption-key`; Provider Hub stores the key, not the prompt, reasoning, response, or session. The envelope scope binds the selected model and account. An envelope cannot cross to a different provider connection, model, or account, so start a new Codex task when changing those boundaries. Cerebras JSON and streaming fixtures verify that its signed thinking survives this encrypted round trip.

The custom Codex catalogue publishes exact IDs such as `grok/grok-4.6`, `mistral/mistral-vibe-cli-latest`, and `ollama/deepseek-v4-flash:cloud`, not OpenAI-shaped aliases. It contains every compatible entry published by the configured provider catalogues, including OpenRouter’s curated context variants, rather than only the selected default. There is no separate per-user inclusion checklist. While the Provider Hub configuration is active, this temporary catalogue replaces the ordinary Codex picker list; it is not merged with an OpenAI model list. Friendly labels do not change routing IDs. Before configuration switching, the installed app-server's `model/list` must return the expected IDs, names, effort levels, and service tiers. Provider Hub records that runtime signature and rechecks it with the running gateway's catalogue digest during activation, preventing an incompatible catalogue from silently falling back to OpenAI defaults. `HARNESS-OPTIONS.md` records the launcher design, installed-app evidence, and actual CLI/live qualification.

**Names, branding, context, and model controls**

The display-name parser recognizes provider spelling, versions, sizes, release dates, and qualifiers such as Cloud and Preview. Mistral aliases use the versioned model identifier reported in provider metadata when available: Medium’s current billing-model ID identifies 3.5, while the fixed Small/Large release IDs retain their Small 4/Large 3 product names. Raw repeated API names no longer override those labels. This changes display names only; moving routing aliases remain unchanged. Provider metadata and explicit display overrides take precedence. Examples: `model-name-v1-2504` becomes `Model Name V1 · Apr 2025`; `gpt-oss:120b-cloud` becomes `GPT OSS · 120B Cloud`. Outbound routing uses the original upstream ID; OpenRouter’s local context-choice suffixes are removed before the request reaches its API.

The appearance layer reuses TaskWraith's provider presentation schema: `displayProvider`, `hueKey`, `accent`, `shortCode`, `modelLabels`, and optional bundled `logo` assets. It is keyed by immutable runtime provider identity. Provider names, accents, initials, and model labels can be edited in **Appearance**. An Ollama- or OpenRouter-hosted brand can have its own accent while the route retains the account/provider identity. The original logos and palette values came from the read-only TaskWraith source. Codex, Claude, AntiGravity, Qwen Token Plan, OpenRouter, Devin, and Meta/Muse logos were copied from the read-only Limit Counter source; asset provenance and glyph display settings are documented in [Source/provider-logos/README.md](Source/provider-logos/README.md). A brand with no upstream palette to copy, such as an OpenRouter `stealth/` preview, gets an arbitrary accent held to the same rule as the rest: accents are foreground colours on both surfaces, so each hue is normalized to one shared luminance — at least 4.5:1 against white and a clear step off the dark chrome — and then takes all the chroma sRGB allows there. Stealth’s `#9E6C00` is that gold. The Ollama display-brand table is mirrored from TaskWraith’s `OLLAMA_DISPLAY_BRANDS`, needles included, so a local or Cloud tag — `gpt-oss:120b-cloud`, `granite4.1:3b`, `lfm2.5:8b`, `minicpm-v4.5:8b` — wears its maker’s hue while the runtime, the daemon and the model route stay Ollama’s.

Context is read-only. Exact integer values come from provider metadata or exact documented fixed-ID limits. Genuine context variants remain separate entries. Plan-dependent or imprecise limits remain provider-managed instead of inventing a number. Ollama's architectural maximum and effective runtime allocation are distinct: `/api/show` does not establish the latter. Claude's own context meter can still use Claude-specific presets; the gateway cannot fully customize it through discovery. When Claude Desktop injects standalone `<total_tokens>` / `<ctx_window>` reminder lines, the gateway rewrites them to remaining catalogue context for the selected route. Desktop's default is a 15,000,000-token task budget that resets every user turn, which is not the provider window. Unknown or non-numeric context is left unchanged, and fenced copies of those lines are not rewritten. For Codex, a known numeric context is advertised at 100 percent with automatic compaction at 85 percent. An unknown context is advertised as `null` with no automatic-compaction threshold. The installed Codex engine preserves that unknown value as `model_context_window: null` instead of guessing 200,000 tokens; compact manually when needed on an unknown-context route.

Effort is translated only through established provider controls from each desktop harness. The Codex catalogue publishes a provider's documented effort modes when known, and synthesizes an **Ultra** slider position as an alias for each model's top advertised rank, so the slider is available even when a provider does not name an ultra level natively. The gateway maps ultra onto that highest advertised rank at request time. Above-range ranks (xhigh, max, ultra) that a model does not support natively are capped to its top advertised rank with a `normalized_to_` compatibility note, rather than rejected. Below-range requests still fail closed. Thinking-capable Ollama models, including Cloud, advertise those ranks. Mistral/Vibe expose Off, Low, Medium, High, and Max (no xhigh or ultra); xhigh/ultra map to max. DeepSeek maps minimal/low to low, medium/high/xhigh to high, and max/ultra to max. Cerebras caps xhigh/max/ultra to its top advertised rank (high or xhigh depending on the model). Gemini caps xhigh/max/ultra to high. Effort values are never manufactured as extra models. Fast requests require a documented same-model capability and never silently change the selected model. Kimi's high-speed model has a distinct ID/context and remains a distinct catalogue entry. That model (K2.7 Code HighSpeed) is documented as thinking always on with no effort ladder. The Codex catalogue publishes a single placeholder High position for it plus the synthesized Ultra alias, so the slider is never empty and Ultra still opts into multi-agent orchestration on the fast route, while the gateway drops any effort rank or thinking-off control sent to it on the wire with an `_ignored_thinking_fixed_on` compatibility note instead of rejecting the turn, because the route has no other state to select. Thinking off remains an exact-model control only on Kimi for Coding (K2.8 Preview); on the K3 routes it would be served by K2.8 Preview, so it still fails closed.

Any route that publishes a reasoning ladder advertises `multi_agent_version: "v2"`, together with a `multi_agent_reasoning_effort` taken from that model's own top advertised rank rather than a fixed value. This used to require a reasoning flag as well, which withheld the runtime from every plain instruct route for no gain, since the collaboration tools and the multi-agent briefing arrive from the desktop's own `features.multi_agent_v2` either way. On activation, Provider Hub enables that feature flag in the Codex `config.toml`. It deliberately does not write `default_subagent_model` or `default_subagent_reasoning_effort`, and clears them when an older journal left them behind: both resolve once at activation, but the model is switched in the app and an in-app switch never re-runs activation, so a pinned sub-agent target goes stale the moment the user changes route. Codex's own `spawn_agent` contract prefers the inherited parent model, so with no default the children of a Mistral thread are Mistral and the children of a DeepSeek thread are DeepSeek, which is what a pinned default was trying and failing to express; the model can still name a different route per sub-agent through `spawn_agent`'s `model` argument. Together these let the Codex effort slider's Ultra position opt into autonomous sub-agent orchestration over the configured provider connection. The `multi_agent_mode` hint is left at its default, so Ultra never forces delegation on every turn. Advertising the runtime is not the same as asking for it, though, and a slider position that changes nothing a model does is the same as no slider: when Ultra is the rank the user selected and the request still carries the collaboration spawn tool, the gateway appends a short note to the request `instructions` asking the model to run investigation, implementation and verification as sub-agents and to answer solo on conversational or trivial turns. The note names the spawn tool by the name it actually travels under, and it is withheld whenever the spawn tool is absent, so a sub-agent forbidden to spawn again, and any provider whose `spawn_depth_limit` is `0`, is never told to call a tool it was not handed. A route with no published ladder receives no multi-agent keys or feature flag. All owned keys are backed up and restored on quit; the user's other `features` entries are preserved.

A listed model is labelled as advertised or documented until an actual inference succeeds. Historical errors distinguish quota/rate limiting from model rejection. Refreshing the catalogue does not run an inference sweep.

Claude's custom model picker groups curated models alphabetically by account provider, retaining the saved order within each provider. The same grouping applies to the managed Claude Code picker. Grouping uses the connection (for example, Ollama), so models from different makers served by that connection stay together. Saved catalogue order, model IDs, and family defaults remain unchanged. Claude remembers a still-available selected model; when there is no saved selection, Desktop falls back to the first available row in the grouped list. Desktop's discovery format does not expose provider section headings.

Claude Desktop's discovery expands a model whose advertised context is at least 1M into a standard and a `[1m]` picker row. To show one offering per 1M-capable model at the 1M preset instead, the gateway advertises each such route under a single `[1m]`-suffixed slot id (for example `claude-fable-5[1m]`) with `supports_1m: false`, so Desktop does not synthesize a second row and its session meter reads 1M. Routes whose effective context is below 1M are advertised bare as before. Plan-dependent routes (such as the generic Kimi `k3`) advertise 1M when their largest `context_options` entry is at least 1,048,576, so Kimi K3 gets the 1M meter without claiming a single fixed window.

Because Desktop meters the session at its advertised window (1M for `[1m]`-suffixed routes, 200K otherwise) and a smaller provider window can still force earlier compaction, the gateway enforces its own per-model compaction: it trims oldest turns first (before rejecting an over-window conversation) at 85 percent of the catalogue window, and each Claude slot accepts an explicit **Compact at** token threshold for routes whose effective window is smaller — for example `100000` on a 131K Cerebras or Ollama route — instead of typing `/autocompact` every session. The override clamps to the catalogue window and is blank (auto 85 percent) by default; a bare route shared by several slots uses the smallest configured threshold. The compaction threshold also reserves room for the requested output (after the model's own output cap), so a long session cannot silently shrink the response below what the harness asked for; when compaction cannot free enough room the plan records an `output_headroom_clamped` note instead. Compaction drops whole tool cycles (an assistant tool call together with its results) and keeps a contiguous tail of the conversation, so the trimmed history never carries a tool result without its call, which chat-completions upstreams such as Mistral reject. It pins the opening user message when that message is small, and inserts a short user-role note where the cut was made, so the model knows earlier history is missing and the history still starts with a user turn. The gateway's byte-based estimate is deliberately pessimistic (about 40 percent above Mistral's own count on source code), so each route learns a calibration factor from the input counts the provider reports on completed requests and scales later estimates by it; the factor only ever lowers an estimate, never below half, and an unlearned route stays as conservative as before. Every gateway-side compaction is visible as a blue row in the Hub Activity feed with before/after estimates, so a missing row means the conversation never reached the threshold rather than compaction failing silently. When the gateway itself refuses an over-window request it says so ("Provider Hub did not send this request") instead of presenting the refusal as a provider error. When Desktop compaction rewrites old assistant output, gateway-bound Cerebras reasoning signatures no longer match; the gateway then strips the broken traces and drops the unverified tool cycles (keeping the summary text) so the follow-up turn runs instead of failing with `Cerebras reasoning signature does not match this model, scope, or assistant output.` Unverified text is never forwarded as provider reasoning. Note that input compaction cannot prevent the harness's own output cap (for example Claude Code's 32000-token `CLAUDE_CODE_MAX_OUTPUT_TOKENS` default): if the model legitimately writes more than that, raise the harness cap or shorten the task.

Cerebras' account model API currently returns IDs without numeric limits. When an account field is present it still wins. Otherwise the org Limits-page values are used for the exact listed IDs: `gpt-oss-120b` 131,000 context / 40,000 max output, `gemma-4-31b` 131,072 / 40,000 with image input, and `qwen-3.8-27b` 131,072 / 40,960 with image input. Those beat the public catalogue's stale 65,536-token figures. Unknown IDs still fall back to public metadata.

**Claude Auto mode**

The existing **Enable Claude Auto mode** toggle is preserved and defaults off. It enables Claude's native approval classifier through the ordinary gateway route. It does not select an independent reviewer model.

Claude Desktop 1.52386.3 and the inspected Claude Code builds choose the classifier model internally, using server configuration and provider/model fallbacks. The gateway receives no stable Auto-specific request-role marker. Mapping the classifier's Claude-facing ID affects every request using that ID, including main/background traffic if they share it. Consequently this preview has no misleading independent reviewer picker and does not infer reviewer role from prompt text. **Accept edits**, **Auto**, and **Bypass permissions** remain different Claude permission modes. See `NATIVE-AGENTS.md` for the installed-code trace and current official documentation.

**Sessions, restoration, and isolation**

For Claude, the app uses the native third-party profile mechanism used by Ollama. It switches the installed Claude app's profile; it does not launch a concurrent cloned Claude instance. Claude stores first-party and third-party history separately. Ollama and this gateway share Claude's third-party history store, so existing third-party conversations can appear together. Start a fresh conversation when changing incompatible providers or reasoning models.

Profile activation records a recovery journal before changing the dedicated profile, selection metadata, and deployment-mode fields. Restoration changes only still-owned values and preserves changes another manager made in the meantime. An already-running Claude on another profile must be closed before switching. Transcripts are never read, copied, or edited by the profile manager.

For Codex / ChatGPT Desktop, Provider Hub edits its owned root model, reasoning, tier, and web-search fields and adds a `provider_hub` stanza to the user's existing `config.toml`. Vendored `tomlkit` 0.13.3 preserves the rest of the TOML document. A verified backup and transaction journal are written before the switch. Restoration reverts values that are still owned by the launch transaction while retaining later unrelated settings and external provider/model changes. Conversation and authentication files are never modified. This is a managed restart of the installed desktop app, not a claim that Provider Hub can open a simultaneous isolated GUI instance.

**Local data and privacy**

Preview state lives under `~/Library/Application Support/Provider Hub Preview/`. Its default port is 11438; its profile ID is `14c58c94-d7e8-4a15-96b8-81668956e474`. Stable Mistral Bridge 0.2 continues to use its original state directory, port 11436, Keychain namespace, and profile ID.

- `settings.json`: provider connections, credential-source modes/revisions, model mappings, per-slot omit-system/omit-tools flags, appearance overrides, and preferences; no API keys.
- `catalogues/*.json`: metadata scoped to the provider connection and credential revision. Key replacement invalidates that provider's catalogue.
- `catalog.json`: optional metadata-only import from the stable Mistral build. No keys or transcripts are imported.
- `gateway-token`: private local authentication credential supplied to Claude's profile and returned to Codex only through the command-backed local helper.
- `reasoning-signing-key`: separate private key used to authenticate Cerebras reasoning replay and scope xAI response-ID ownership; never supplied to either desktop client as a provider credential.
- `responses-encryption-key`: separate persistent local key used to authenticate and encrypt provider reasoning carried through translated Codex Responses history. It is not prompt or session storage.
- `activity.jsonl`: event, real provider/model, HTTP status, and usage metadata. No prompts, tool arguments, response text, or authorization headers.
- `last-request-shape.json`: field/role/content-type names only.
- `last-responses-shape.json`: Responses field, input-item-type, and tool-type names only.
- `profile-transaction.json`: temporary restoration journal, removed after successful recovery.
- `codex-models.json` and `codex-prepared.json`: generated provider-qualified Codex catalogue plus its prepared model, catalogue digest, and installed-runtime signature; no credentials.
- `codex-transaction.json`: private restoration journal, removed after a successful restore.
- `codex-config-before.toml`: mode-`0600` verified backup of the user's pre-switch Codex configuration.
- `response-ownership.json`: up to 10,000 stored xAI response IDs with model/account ownership scopes; no prompt or response content.

Launch preparation uses same-connection metadata for 24 hours. Missing/stale selected routes trigger a refresh. A transient discovery failure can use a valid exact-route cache up to 7 days old, with a warning; authentication failures, changed credentials, missing routes, or older caches block with a specific explanation. Refresh batches have a 58-second deadline. Before switching either desktop harness, activation checks that the running gateway loaded the prepared selected-route metadata or Codex catalogue digest.

The gateway binds to literal loopback, authenticates desktop requests, answers CORS preflights, and echoes the request `Origin` so the desktop webview's model discovery can read responses — cross-site pages still learn nothing, because every non-health route requires the local bearer token. It uses the selected provider's credentials for outbound inference. Hosted endpoints are constrained to official HTTPS URLs; Ollama accepts literal loopback HTTP. Native Messages requests preserve protocol version/beta headers, tools, thinking, and IDs without forwarding the local gateway token. Responses requests likewise keep provider credentials at the gateway boundary and do not forward the local Codex bearer token or local `client_metadata`. A translated Responses request reaches the same process through an authenticated loopback Messages request; only that inner provider request acquires the shared concurrency slot and activity count.

Cerebras reasoning tool turns need replayable assistant reasoning. For Claude, the adapter returns a thinking block signed over the exact provider/model/account scope, reasoning, visible text, tool IDs/names, and arguments. The next Messages turn validates it before replaying the provider's reasoning field. Foreign or edited traces fail explicitly. Cerebras Messages streams are buffered until the complete signed block is available, while gateway ping events keep the connection active. For Codex, the Responses bridge additionally carries that authenticated thinking block in the encrypted reasoning envelope described above.

**Build and verification**

From the repository root:

```bash
uv run --python 3.13 --with-requirements Source/requirements.txt python -m unittest discover -s Source -p 'test_*.py'
bash Source/build.sh
```

Use the `uv` CPython 3.13 runtime for source tests. Building requires Apple's command-line developer tools. `Source/build.sh` creates an ad-hoc signed development app. Omit `PROVIDER_HUB_PYTHON_RUNTIME` for a lightweight source build, or set it to a clean relocatable Python installation to embed that runtime in the app. Python discovery prefers the bundled runtime. The prepared shareable bundle embeds an ARM64 CPython 3.13.13 with `cryptography` 50.0.0 from `Source/requirements.txt`; it does not copy Vibe or another user installation's `site-packages`. Python's upstream licenses are retained inside the runtime. Before signing, `scripts/prepare_runtime.py` prunes the development subtrees the worker never imports and rewrites the runtime's recorded build prefix to the neutral value CPython was configured with, so the bundle carries no build-machine path; it fails the build if a personal path survives, or if the pruned runtime cannot import `cryptography` and run the worker.

`Source/package_macos.py` accepts a Developer ID Application identity, signs the embedded native components and app, verifies the result, and creates the distribution archive. Its optional `--submit --notary-profile NAME` path submits with an existing `notarytool` Keychain profile; the password is not passed to the script. After Apple accepts a submission, staple the app with `xcrun stapler staple`, validate it, and recreate the distribution zip. Gatekeeper must report `Notarized Developer ID` for the finished release. Rebuilding from source creates a new development artifact and does not inherit earlier notarization.

Every new build includes `Contents/Resources/build-manifest.json` with its source revision, build-input state and packaged worker hashes. For an exported `git archive` source tree, set `PROVIDER_HUB_SOURCE_REVISION` to the full commit and `PROVIDER_HUB_SOURCE_REPOSITORY` to the originating checkout so the build can verify the exported inputs against that commit. Release from a clean export, then install the accepted, stapled bundle in `/Applications` and launch it. Verify the installed manifest and `http://127.0.0.1:11438/_bridge/health` agree on version, build and revision (use the configured port if changed). The [AntiGravity investigation](docs/antigravity-host-handoff.md) records why a validly notarized older installation continued failing after the source fix.

Validate the installed worker contents against the intended clean commit:

```bash
python3 Source/build_provenance.py verify --require-clean \
  --app-dir '/Applications/Provider Hub Preview.app' --revision '<full commit SHA>'
```
